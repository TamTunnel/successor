Successor

When the person who built the agent leaves, the agent doesn't. Successor governs the handover — and proves it happened.

The problem

When an employee who built internal agents leaves, those agents keep running — on schedules, with credentials, under an owner who is gone. In most orgs that handover is a ticket, a chat message, and hope. There is no record of who approved it, no proof the credentials were rotated, and no way to tell afterward whether the leaver can still get in.

The solution, in plain terms

Successor is a small command-line tool, one static Go binary with no runtime to install. An admin registers each agent — what it is, who owns it, where its config and runbook live, and references to its credentials (never the credentials themselves). When the owner leaves, an admin requests a handover to a named successor. A different person, holding the approver role, approves it. The successor accepts with a one-time token delivered outside the tool. Then the credentials are revoked and re-issued under the successor (by a human checklist or by scripts), the schedule is disabled, and both the successor's and the leaver's access are verified. Every step lands in a hash-chained audit log, and signed checkpoints can be stored off the machine so that even a full rewrite of the log is detectable.

The one rule the whole tool is built around: Successor never sees, stores, logs, or transmits secret material. It records references and outcomes only. If a credential cannot be re-issued, the handover lands in partial with the residual risk named and explicitly accepted by both the successor and the approver — never silently complete.

Quick start

go build -o dist/successor .

# 1. Create the store (one Ed25519 audit keypair, on-box at 0600).
successor --store ~/.successor init --admin E-1009 --admin-name "Admin Example"

# 2. Register people and the agent (credential REFERENCES only).
successor --store ~/.successor person add --actor E-1009 --id E-1001 --name "Alex Example"
successor --store ~/.successor person add --actor E-1009 --id E-1002 --name "Sam Sample"
successor --store ~/.successor person add --actor E-1009 --id E-1010 --name "Approver Example" --approver
successor --store ~/.successor agent register --actor E-1009 \
  --name deploy-bot --owner E-1001 --runtime cron \
  --credential-ref "iam:prod-key-1" --credential-ref "vendor:legacy-key" \
  --schedule-ref "cron:nightly-deploy"

# 3. Request, approve, accept (token delivered through the org's secure channel).
successor --store ~/.successor handover request --actor E-1009 \
  --agent <agent-id> --to E-1002 --reason "E-1001 departing"
successor --store ~/.successor handover approve <handover-id> --actor E-1010 --approver E-1010
successor --store ~/.successor handover accept <handover-id> \
  --actor E-1002 --successor E-1002 --token <one-time-token>

# 4. Work the checklist, then execute. Prove the log, export a checkpoint.
successor --store ~/.successor handover checklist <handover-id> --item 1 --done --actor E-1009
successor --store ~/.successor handover execute <handover-id> --actor E-1009
successor --store ~/.successor audit verify
successor --store ~/.successor audit checkpoint --actor E-1009 --out /secure/off-box/cp.json

Honest limits

  • Successor cannot hand over agents it does not know about. Inventory completeness is the org's responsibility.
  • Successor cannot un-know a secret the leaver copied. Rotation is the only cure; where rotation is impossible, the risk is named, not hidden.
  • Without an adapter that can actually revoke, re-issue, and disable, a handover is a governed record, not enforcement.
  • The audit trail detects tampering against an independently held checkpoint. Without exported checkpoints, a full-store rewrite is undetectable. Export checkpoints off-box.
  • Actor identity is asserted, not authenticated, in v1. Do not deploy on a box where untrusted users can invoke it as arbitrary actors.
  • The audit signing key lives on the box at mode 0600; script hooks run as the invoking user and can read it. External-key custody is planned for v1.1.
  • Credentials added to the agent after the request are not covered by that handover — re-request after inventory changes.
